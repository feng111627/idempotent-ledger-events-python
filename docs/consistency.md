# 一致性保证、幂等语义与失败分类

本文说明账本服务在并发、重复提交、写入失败与历史回放下的行为与依据。

## 1. 金额模型：杜绝浮点误差

- 对外金额使用十进制字符串（`"12.30"`），服务端用 `decimal.Decimal`
  精确解析，随即转换为整数「最小货币单位」（1 主币单位 = 100，如「分」）。
- 领域层、数据库、余额运算全部使用 `INTEGER`，**全程不出现 `float`**，
  因此不存在 `0.1 + 0.2 != 0.3` 导致的对账不平。
- 超过 2 位小数、`NaN`、`Infinity`、无法解析的输入在边界即被拒绝
  （`invalid_amount`）。
- 展示时再由整数格式化为两位小数字符串，仅用于显示，不参与任何运算。

## 2. 并发一致性：不透支、不丢更新、总额守恒

采用 SQLite，关键设置与约束：

1. **每工作线程独立连接**（`threading.local`）：FastAPI 的同步端点在线程池
   中执行，共享单连接会造成事务交错；独立连接保证每个事务上下文清晰。
2. **写事务一律 `BEGIN IMMEDIATE`**：在写入前获取 RESERVED 写锁，
   写者之间在数据库层**串行执行**；配合 `busy_timeout=30s`，后来者等待
   而非立即报 `SQLITE_BUSY`。WAL 模式下读者不阻塞写者。
3. **扣款是条件更新**：
   ```sql
   UPDATE accounts SET balance = :new
   WHERE account_id = :id AND balance >= :amount;
   ```
   即使应用层读余额与更新之间存在竞争，数据库也会拒绝导致透支的更新，
   应用检查 `rowcount` 后对失败者回滚并返回 `insufficient_funds`。
4. **表级约束兜底**：`accounts.balance` 与事件金额均有
   `CHECK (... >= 0)`，负数余额在数据库层不可能落库。
5. **总额守恒来自事件结构**：每笔转账在同一事务内追加
   `transfer_out(-x)` 与 `transfer_in(+x)` 两条事件，钱只是在账户间搬移；
   开户的 `open` 是唯一「注入」资金的事件。全部事件的有符号和恒定。

因此并发下的结果与某个串行执行顺序等价（可线性化），可用 `/replay` 复核。

## 3. 事件账本与原子性

- 每次资金变动都向只增的 `events` 表追加一条记录，含全局单调递增 `seq`、
  账户、类型、非负金额、**应用后余额快照** `balance_after`、关联转账
  幂等键与 UTC 时间戳。
- 一笔转账的全部动作在**同一个数据库事务**中完成：
  幂等记录 → 条件扣款 → 入账 → 两条事件 → 提交。
- 任一步失败（账户不存在、余额不足、驱动异常等）都 `ROLLBACK`：
  **事件与余额要么同时生效，要么同时不存在**，不会只落一边。
  单测 `test_failed_transfer_appends_no_events` 固化了这一点。

### 回放（replay）语义

`/replay` 不修改任何数据，只按 `seq` 顺序重放事件并做三层核对：

1. 重算过程中任何账户不得出现负余额；
2. 每条事件的 `balance_after` 必须等于按序重算值（事件链自洽）；
3. 每个账户的重放余额必须等于 `accounts` 表当前余额。

任一不符返回 `replay_mismatch`（表示账本可能已被外部破坏）。
事件流即权威历史：即使清空并重建余额表，也能由事件流完整复现状态
（见 `test_replay_persists_across_restart`）。

## 4. 幂等提交语义

幂等键由调用方提供（转账必填，开户可选）。权威判定放在
**写事务内部**（拿到 `BEGIN IMMEDIATE` 锁之后），因此对同一键的并发请求
也是原子的「查—插」，不可能两笔都判定为「首次」。

| 情形 | 行为 | 响应 |
|------|------|------|
| 首次提交 | 业务变更与幂等记录同事务落库 | 正常结果，`replayed=false` |
| 同键 + 同内容重复提交（顺序或并发） | **不重复记账**，返回首次持久化的响应 | 相同结果，`replayed=true` |
| 同键但金额/方向/账户不同 | 拒绝，不覆盖既有记录 | `409 idempotency_conflict` |
| 同键跨操作类型（开户键用于转账等） | 拒绝 | `409 idempotency_conflict` |
| 首次请求在提交前失败（如透支） | 整事务回滚，不残留幂等记录 | 对应业务错误；该键随后可正常复用 |

实现要点：

- 「请求内容」用规范化 JSON（键排序、紧凑分隔）的 SHA-256 摘要比对，
  与幂等键一起存储；
- 首次响应是可由请求确定性推出的快照，与业务变更在**同一事务**持久化，
  保证重复请求取回的结果与首次逐字节一致（仅额外标注 `replayed`）；
- 幂等记录与业务变更同生共死，因此不存在「记账失败但键被占用」或
  「键存在但没记账」的半成品状态。

> 说明：幂等去重以「操作已成功提交」为准。若在服务器提交成功后、
> 响应返回前发生网络中断，客户端用同一键重试会安全地拿到首次结果，
> 不会重复扣款。

## 5. 失败原因分类

所有错误统一为信封：

```json
{ "error": { "code": "machine_readable_code", "message": "可读说明" } }
```

| code | HTTP | 含义 |
|------|------|------|
| `validation_error` | 422 | 请求体/字段校验失败（缺字段、超长等），含字段级 details |
| `invalid_amount` | 422 | 金额非法：非数、超过 2 位小数、非正转账额、负数开户等 |
| `account_not_found` | 404 | 转出/转入/查询的账户不存在 |
| `account_already_exists` | 409 | 账户标识已存在（换新幂等键重复开户也不覆盖） |
| `insufficient_funds` | 422 | 余额不足（含并发竞争下条件更新失败） |
| `idempotency_conflict` | 409 | 幂等键被不同请求内容或不同操作复用，拒绝静默覆盖 |
| `storage_unavailable` | 503 | 底层存储/驱动异常的**归一化**结果，请稍后重试 |
| `replay_mismatch` | 500 | 事件回放与账户表不一致，账本完整性被破坏 |

**异常归一化**：仓储层捕获所有 `sqlite3.Error`，仅在服务端日志记录异常
类型（如 `ProgrammingError`、`OperationalError`），对外一律转换为
`storage_unavailable` 与通用文案，不泄漏驱动名、SQL、连接信息或内部堆栈。
回滚动作本身也做了保护，不会因连接已失效而掩盖原始业务异常。

## 6. 本地验证

```bash
uv sync --group dev
uv run pytest          # 全量；--log-cli 输出业务场景与逐用例结果
```

覆盖矩阵：

- `tests/test_accounts.py`：金额精度（无浮点误差）、开户/查询、重复开户、
  非法金额；
- `tests/test_idempotency.py`：重复提交不重复记账、同键换内容/换方向/
  跨操作拒绝、首次失败回滚后键可复用；
- `tests/test_concurrency.py`：200 笔密集双向转账守恒、热点账户无丢更新、
  超额抢兑不透支、同键并发只落账一次；
- `tests/test_replay.py`：事件回放重建与三层核对、事件链自洽、失败不留
  事件、重启后持久化可复现；
- `tests/test_errors.py`：驱动异常归一化、统一 HTTP 错误信封。
